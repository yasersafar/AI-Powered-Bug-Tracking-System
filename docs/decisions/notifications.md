# Notifications: self-hosted ntfy vs ntfy.sh vs e-mail vs VS Code notifications

Requirements: FR-16 (e-mail on assignment, status change and Critical severity), FR-17
(in-app alerts: an ntfy topic per user and VS Code notifications), DC-03 (bug text must not
leave our infrastructure).

## Options

| Criterion | ntfy, self-hosted (the software) | ntfy.sh (the public hosted instance) | E-mail (SMTP) | VS Code notifications |
|---|---|---|---|---|
| Where the text goes | Our own server (Docker container next to the backend) | A third-party server on the internet | Our SMTP relay, then the recipient's mailbox provider | Stays inside the user's editor |
| Privacy (DC-03) | Meets it | **Does not meet it**: titles of bugs would be sent to an external service | Acceptable for internal relays; the text reaches the mail provider | Meets it |
| Access control | Deny-all by default; the backend uses a publish-only token; each user's topic name is random and unguessable | Topics are public unless reserved on a paid plan | Per recipient | Per logged-in user |
| Reaches the user when VS Code is closed | Yes (phone / desktop ntfy app) | Yes | Yes | No |
| Cost | Free; one small container | Free tier with limits | Free with an internal relay | Free |
| Setup | `docker compose` service, declarative users and tokens generated by `make env` | None | SMTP host and credentials (Mailpit in development) | None |
| Reliability | As reliable as our server; delivery failures are logged and never break the request | Depends on an external service | Retries handled by the mail server | Only while the editor is open |

## Decision

All three channels that keep data inside our infrastructure are used together:

1. **Self-hosted ntfy** (`binwiederhier/ntfy:v2.38.1` in `docker-compose.yml`) for push to
   phones and desktops. The configuration refuses `ntfy.sh` URLs at start-up
   (`app/core/config.py`), so the public instance cannot be configured by mistake.
2. **E-mail via SMTP** for the events in FR-16 (Mailpit in development, any SMTP relay in
   production).
3. **VS Code notifications**: the extension polls `/api/v1/notifications` every 30 s and
   shows new items, with an unread badge on the Notifications view (deviation D-36).

Every notification is stored in the `notification` table first; e-mail and push are sent in
a background task after the request commits, each with its own delivery status
(`sent`, `failed`, `skipped`). A failing channel is logged and never fails the user's action.
Users can switch e-mail and push off in **My Profile**.

## Verified behaviour

* `backend/tests/test_notifications.py`: recipients, preferences, failure handling.
* `backend/tests/test_notifications_live.py` (`make test-live`): real delivery through the
  running ntfy and Mailpit containers.
