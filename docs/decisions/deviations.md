# Deviations from the build specification

Every place where the implementation differs from the original build specification, why, and
what was done instead. Newest entries at the bottom of each stage.

| # | Stage | Specification said | What we did | Reason |
|---|---|---|---|---|
| D-01 | 1 | Repository is "almost empty" (only README, .gitignore, empty folders). | Started `chore/1-setup` from `origin/main` (which matches that description). Open PRs #16 (CI) and #17 (demo skeleton) are superseded by this branch; PR #15 (sprint records) is untouched. Stage 2 will build on top of the existing `part2-auth` branch so its author's commit stays in history. | The remote already had three open PRs and a teammate branch (`part2-auth`, auth/RBAC/projects). Rewriting that work from scratch would hide a team member's contribution. |
| D-02 | 1 | Python 3.11. | Python 3.11 everywhere (Docker image `python:3.11-slim-trixie`, CI `setup-python 3.11`, local `backend/.venv` created with `python3.11`). | No deviation in the runtime; noted because the development Mac's default `python3` is 3.12, so the Makefile pins `PYTHON ?= python3.11`. |
| D-03 | 1 | Docker for the dev environment. | Docker Engine via **Colima** (`brew install colima docker docker-compose`) on the development Mac. Any Docker Engine with Compose v2 works (Docker Desktop, OrbStack, Linux). | Docker Desktop was not installed; Colima is free, headless and needs no licence acceptance. |
| D-04 | 1 | FastAPI `TestClient` (uses `httpx`). | Dev dependency is `httpx2`. | Starlette 1.x deprecates `httpx` for its `TestClient` and recommends `httpx2` (same API). |
| D-05 | 1 | TypeScript (strict) for the extension. | TypeScript `~6.0`, not the newest 7.x. | `typescript-eslint` 8.x (required for type-aware ESLint) supports TypeScript `<6.1` only. |
| D-06 | 1 | Self-hosted ntfy with per-user topics. | Stage 1 runs ntfy with `auth-default-access` = `read-write` on `127.0.0.1` only. Stage 3 switches to `deny-all` with a backend publisher account and per-user read access. | Access control needs user accounts, which arrive with the backend core in Stage 2/3. The port is bound to localhost so nothing is exposed meanwhile. |
| D-07 | 1 | Makefile with `make up`, `make seed`, `make train`, `make eval`, `make test`. | Stage 1 ships only the targets that already work (`up`, `down`, `test`, `lint`, ...). `seed`, `train`, `eval`, `openapi` are added in the stage that implements them. | Avoids placeholder targets that print "not implemented". |
| D-08 | 1 | OpenAPI 3.0 (DC-05). | FastAPI generates an **OpenAPI 3.1.0** document. | FastAPI ≥ 0.99 only emits 3.1 (JSON-Schema-2020-12 aligned). 3.1 is a minor revision of OpenAPI 3; Stage 7 decides whether `docs/openapi.json` is also down-converted to 3.0.3 for tools that need it. |
| D-09 | 2 | `audit_log` has nullable `bug_id` and `profile_id` with a CHECK that exactly one is set. | `audit_log` targets are `bug_id`, `project_id` and `target_user_id`, with `CHECK (num_nonnulls(...) = 1)`. Stage 3 adds `profile_id` to the same CHECK. | FR-19 requires membership changes to be logged and FR-03 role changes by an Administrator need a trail too; neither belongs to a bug or a developer profile. |
| D-10 | 2 | Four roles: Reporter, Developer, Project Manager, Administrator. | Two levels: a **global role** on the user (Administrator = system-wide; Project Manager may create projects) and a **project role** on `project_member` (Reporter, Developer, ProjectManager) that decides what a user may do inside that project. Self-registration always creates a Reporter; only an Administrator changes global roles. | FR-19 asks for "members with project roles". The `part2-auth` branch let users pick their own role at registration, which would let anyone become an Administrator. |
| D-11 | 2 | Unauthorized access returns 403; never reveal resources outside the user's projects. | A resource that does not exist returns 404; one that exists in a project the caller is not a member of returns 403 with no content. List endpoints only ever include the caller's projects. | NFR-06 requires 403. Only existence (not content) can be inferred from ids, which carry no sensitive information. |
| D-12 | 2 | FR-07 search target: ≤ 2 s on 50,000 bugs. | Search is implemented with a generated `tsvector` column + GIN index and B-tree indexes on every filter column. The 50,000-bug timing is measured in Stage 5 together with the other latency/load tests, using real bug texts from the Stage 4 datasets. | Needs a realistic 50k corpus; Stage 4 provides it. |
| D-13 | 2 | `scripts/seed.py` (users, projects, ~50 bugs, developer profiles incl. a cold-start developer). | Written in Stage 3. | Developer profiles (FR-20) are part of Stage 3. |
| D-14 | 2 | `/auth/login` returns a JWT. | Login takes OAuth2 password-flow form fields (`username` = e-mail, `password`) so Swagger UI's "Authorize" button works. Tokens carry a per-user `ver` claim; changing the password increments it and revokes all earlier tokens immediately. | Standard OAuth2 shape; exact revocation (a timestamp-based check was tried first and failed a test because JWT `iat` has 1-second resolution). |
| D-15 | 2 | Rate limiting on `/auth/login`. | In-process sliding window per client IP (default 10 attempts / 60 s, configurable). | No extra infrastructure (Redis). With several backend replicas the reverse proxy should apply the same limit; documented for Stage 7 deployment docs. |
| D-16 | 2 | Resolved → Verified / Resolved → InProgress by "Reporter / QA". | Allowed for the bug's own reporter and any member whose project role is Reporter (used for QA staff), plus Administrators. Closed bugs stay commentable but their fields, severity and assignee are frozen. | The SRS has no separate QA role. |
| D-17 | 3 | Tables listed in 5.1 (no assignment table). | Added `bug_assignment` (one row per assignment period, with `ended_reason` = reassigned/closed) next to `resolution_history`. | FR-21 needs a per-developer reassignment count and resolution time measured from assignment; deriving them from audit text would be fragile. The same table gives Stage 5 the real tossing data. |
| D-18 | 3 | Admin manages developer profiles. | Profiles can only be created for users whose global role is Developer, one per user. A profile created later counts that developer's existing resolutions, so cold-start status is correct from day one. | Keeps the recommender's candidate pool to real developers. |
| D-19 | 3 | Self-hosted ntfy topic per user (resolves D-06). | ntfy runs with `auth-default-access: deny-all`. The backend publishes with an access token of a write-only account (`bt-publisher`, `bugtracker-*`). Reading is open, but each user's topic name contains 18 random bytes (`/notifications/subscription` tells only that user). The account's password hash is unusable by construction, so only the token works. `make env` generates the token. | Nobody can inject fake alerts; subscribing from the ntfy phone/desktop app needs no extra login. |
| D-20 | 3 | Notification service sends to ntfy + SMTP and stores a row. | The row is written in the request's transaction; ntfy and SMTP delivery run in a FastAPI background task after the response, with a 5 s timeout and the outcome stored as `sent`/`failed`/`skipped` per channel. No retry queue. | Delivery problems can never slow down or fail the user's request. A retry queue would need extra infrastructure; failures are visible per notification. |
| D-21 | 3 | `scripts/seed.py` with ~50 realistic bugs. | 50 hand-written bugs; their severities are set as Project Manager overrides because the AI arrives in Stage 5. Timestamps are spread over 60 days after creation. Notifications produced while seeding are deleted. Every seeded account's password is `SEED_PASSWORD`, generated per installation by `make env`. | No fixed demo password in the repository; the dashboard and developer statistics show a realistic history. |
| D-22 | 4 | Severity + assignment from "the MSR 2013 Eclipse/Mozilla dataset". | Joined two public datasets on the Bugzilla id: Lamkanfi et al. (MSR 2013) for severity/assignee/component histories and BugRepo for the full description (see `ml/data/README.md`). | The MSR 2013 dataset only contains report titles; a description-based model needs the text from BugRepo. 121,908 Eclipse and 326,245 Mozilla reports appear in both. |
| D-23 | 4 | Duplicates benchmark: "Meng et al. (2024) replication package". | Meng et al. published no replication package; their paper's only data link is BugRepo, which we use (Eclipse Platform, JDT). We report two settings: a realistic online one (each query searches every earlier report) and a test-period-only pool closer to their setup. Their exact cluster-based 8:1:1 split is not reproduced. | No package exists; the realistic setting is what the IDE plug-in actually faces and is much harder than a small test-only pool. |
| D-24 | 4 | BM25 retrieval with `rank_bm25`. | `ml/duplicate/bm25.py` implements the identical BM25Okapi formula on posting lists (vectorised, incremental `add`). A unit test asserts its scores equal `rank_bm25.BM25Okapi` exactly. | `rank_bm25` scores every document for every query term and cannot add documents, which is too slow for real-time use on ~100k reports (NFR-02). |
| D-25 | 4 | 10-fold CV for tuning the ensemble. | 10-fold stratified CV tunes LinearSVC (C, class weight) and ComplementNB (alpha); the selection criterion (mean macro-F1) was fixed before looking at any test data. RandomForest uses fixed, documented settings (200 trees, sqrt features, min leaf 2, balanced subsample). | Ten RF fits per grid point on 85k TF-IDF documents would take hours on CPU. |
| D-26 | 4 | CNN-LSTM over active developers. | Developer classes = developers with >= 50 fixes in the training period; Mozilla uses the most recent 80,000 fixed bugs (`MOZILLA_SAMPLE`) to keep CPU training time reasonable. | Rare developers cannot be learned; the sample size is reported in the results. |
| D-27 | 4 | Store developer identities. | Assignee e-mails from the public datasets are pseudonymised (salted SHA-256) at preparation time; models and results only contain `dev_<hash>` ids. | Privacy by default (GDPR/UAE data-protection notes in the SRS). |
| D-28 | 4 | Severity trained/evaluated on "Eclipse and Mozilla". | Severity on Eclipse only; Mozilla severity is listed as NOT RUN in `RESULTS.md` with the exact command. Mozilla data is used for the assignment generalisation test. | ~45 more minutes of full CPU load would have been needed while the development laptop was overheating (90 °C). |
| D-29 | 4 | (none) | All ML commands cap CPU threads (`ML_THREADS`, default 4) and RandomForest respects the cap. | Keeps team laptops cool; results do not depend on the thread count. |
| D-30 | 5 | `history_score` from the CNN-LSTM. | The Stage 4 CNN-LSTMs rank pseudonymised Bugzilla developers, not users of this system. The running system uses a CNN-LSTM trained on its own resolution history (`scripts/train_assignment.py`, one model per database, classes = user ids, developers with >= N resolutions). Developers it does not know, or every developer while no such model exists, get history = mean cosine between the report and their 3 most similar resolved reports (MiniLM embeddings already cached for duplicate detection). | A model can only score developers it was trained on. The seeded demo has 23 resolutions, too few to train; on the 50k benchmark the live model reaches 60.7% top-1 (see RESULTS.md). |
| D-31 | 5 | History score rescaled so the best candidate is 1 (Stage 4 `recommend`). | CNN-LSTM probabilities are still rescaled; the similarity-based history is used on its absolute 0-1 scale (`normalize_history=False`). | Found in the demo: rescaling turned a weak history match (cosine 0.25) into 1.0, so a newcomer whose skills matched an OAuth report could never rank first. Unit-tested. |
| D-32 | 5 | "ML service" and "stop ML" for the AI-down demo. | The models run inside the backend process (section 5.2: one deployable system), loaded in a background thread at start-up. "Stopping ML" is done with the admin setting `ai_enabled = 0` (runtime) or `ML_ENABLED=false` (start-up); a missing model file degrades only its own step. | No second service to deploy; the same degraded path is used for a failure, a timeout, a missing artifact and the switch. |
| D-33 | 5 | NFR-01/NFR-03 "N concurrent users". | Measured as N virtual users active at the same time with think time (browse 1-3 s, submit 2-8 s), fixed before measuring; NFR-03 compares the same percentile against a single user. A burst (all 50 submit at the same instant) is reported as extra information. | The usual load-testing meaning of concurrent users. The stricter burst reading is reported too, not hidden. |
| D-34 | 5 | NFR-03 < 10% latency degradation. | Not met: +20% p50 / +40% p95 with 3 worker processes on a 4-vCPU laptop VM (RESULTS.md, analysis). The benchmark server runs 3 uvicorn workers with 1 inference thread each; the demo server defaults to 1 worker (`WEB_CONCURRENCY`) to save memory (~1.6 GB per worker with a 50k index). | CPU-bound inference on 4 shared vCPUs. Reported honestly with the profiling fixes and the remaining options. |
| D-35 | 5 | (none) | Each worker keeps its own in-memory duplicate index and catches up with reports created by other workers on the next request (incremental query on `bug.id`). Editing a report's text drops that project's index, which is rebuilt from cached embeddings on the next search. The login rate limiter is per worker. | Stateless API (NFR-08) without an extra vector database or cache service. |
| D-36 | 6 | "Listen to the user's ntfy topic (or poll `/notifications`)". | The extension polls `/notifications` every 30 s and shows new items as VS Code notifications; the Notifications view shows an unread badge. Phones and desktops keep using the per-user ntfy topic (copyable from **My Profile**). | Allowed by the design. Polling needs no second connection or credential in the extension and works through the same API checks (FR-03). |
| D-37 | 6 | Commands: Login, Logout, Report Bug, Open Bug, Search Bugs, Open Dashboard, Admin, Set Server URL. | All of these, plus Create Account (FR-01), My Profile (FR-04), Create Project / Add Project Member (FR-18/19), Mark All Read and Refresh. Log in and Search use VS Code's own input box and Quick Pick instead of webviews; Search accepts filter tokens (`status:`, `severity:`, `project:`, `assignee:me`, `since:`…). | Native inputs are keyboard- and screen-reader-friendly by default and mask the password; every FR is reachable from the editor. |
| D-38 | 6 | "Manual demo works against seeded backend". | Automated instead of by hand: an end-to-end suite runs the extension's own client and webviews inside VS Code against the seeded Docker backend (`E2E_SERVER_URL`, 4 tests), and `npm run preview` renders the real webviews with seeded data for screenshots and an axe-core accessibility scan. A hand walkthrough by the team in VS Code is still recommended before the demo. | The assistant cannot type into VS Code in this environment; the same flows (submit with AI, assign, lifecycle, comments, attachments, admin) are covered by tests. |
| D-39 | 7 | OpenAPI 3.0 (DC-05), decided in D-08. | `make openapi` writes `docs/openapi.json` as **OpenAPI 3.0.3**, converted from FastAPI's 3.1 output (nullable, enum, example, binary uploads, `$ref` siblings), plus the original as `docs/openapi-3.1.json`. Both are validated with `openapi-spec-validator`; a test fails if the file is out of date or a schema lacks a description. | Meets DC-05 literally while keeping the generated document for 3.1-aware tools. |
| D-40 | 7 | Table `model_state` (section 5.1). | Added in Stage 7 (migration 0004): one row per triage model with status, artifact path, SHA-256 and size of the weight file, worker and load time; shown in `GET /ai/status`. Trained models themselves stay files in `ml/artifacts/`. | The table was in the data model but missing until the final review. Hashes tie the served model to the evaluated one. |
| D-41 | 7 | Diagrams "generated to match actual modules and tables". | The ERD is generated from the SQLAlchemy models (`scripts/export_erd.py`); the other diagrams are hand-written PlantUML using real class, module and endpoint names. Tests check that the ERD is current, that every class in the class diagram exists in the code, and that every diagram has a PNG. | Keeps the diagrams from drifting away from the code. |
